# 长期产品原则：让 Agent 获得实际增益，而不只是多一个 API

确立日期：2026-09-28（UTC+08）。来源：维护者关于“比通用 Agent 现场创作更专业、更方便、更节省”的明确要求。
这是所有后续选题、技术选择与验收的产品原则；具体实验执行见 [B1 #13](https://github.com/Buqisir/pisvis/issues/13)，产品总纲见 [#2](https://github.com/Buqisir/pisvis/issues/2)。
本文规定应当证明什么，不宣称 pisvis 已经获胜。修改这一原则须有维护者明确决定，不能由某个阶段任务、模型偏好或依赖选择无声覆盖。

## 1. 北极星：值得调用，比能够调用更重要

> 同一个 Agent，面对同一项真实教学任务，使用 pisvis 后，应更容易交付正确、好看、方便修改、可保存复用的物理教学作品，并持续降低完成任务的总成本。

Agent-first 是调用方式，MCP/CLI/API/Skill 是入口；它们本身不是产品竞争力。
不以接了多少 API、装了多少依赖、实现了多少图元、生成多少代码或一次漂亮截图衡量成功。
不另做一个较弱的 Agent 去竞争“大脑”；让通用 Agent 也能借用 pisvis 已验证的专门能力。
正常执行已支持任务时，不默认嵌套另一个模型来现场重写可视化；确需模型服务时另提实际收益、成本及边界，不能偷偷叠加。

“不能被轻易替代”落实为持续增加用户价值和可复用资产，而不是承诺永远安全、封闭数据格式或人为制造迁移障碍。
通用 Agent 可能不需要某层封装；若真实对照没有增益，就改进、精简或通过兼容方案弃用该封装，而不是要求用户替我们的架构承担成本。

## 2. 要积累的资产与边界

| 值得积累的东西 | 必须用什么证明 | 不能用什么冒充 |
| --- | --- | --- |
| 学科语义与模型 | 适用条件、单位、独立参考结果、易错情形和反例 | 一段物理提示词或 schema passed |
| 自己的视觉语言 | 默认作品、参数/尺寸改变后的作品及维护者反馈 | 装了 GPU 库或挑一张最好截图 |
| 可组合的组件与关系 | 同部件第二个用途、锚点/量值联动、不复制控制器 | 每题复制页面再改数值 |
| 题型与作品的延续性 | 局部修改、批量变式、版本化保存、新会话恢复、实例隔离 | 重新生成一个看起来相似的页面 |
| Agent 使用效率 | 正常配置后的发现、选择、执行、诊断与恢复记录 | 增加工具数量或更长 Skill |
| 用户反馈与回归案例 | 将有权使用的真实失败抽象成可验证原创任务 | 无授权收集资料或假称拥有独占教材 |

这些是投资方向，不是现成壁垒的声明。模型选择是否符合题意、模型内部计算、图形绑定、教学表达要分别核验。
数学示意不能自称完成物理验证；图形可读也不等于教学效果或学习成绩已得到实证证明。

保持创造空间：模板是可组合的起点，不是所有题都只能套固定成品。尚未支持的需求应明确区分可组合部分和能力缺口；
开发扩展经测试与注册后复用，不让消费端执行任意脚本绕过校验。通用 Agent 的有效替代方案可以成为改进参考，不能靠限制它来证明价值。

## 3. 每个任务先写一个价值假设

新功能、模板、重要重构、依赖引入或增加工具入口之前，Issue/PR 至少回答：

1. 哪个真实使用工作流受到影响？不使用 pisvis 时，Agent 通常可以采用什么替代做法？这是观察还是待测假设？
2. 本轮预期提高正确性、教学/视觉、方便、复用、耗时或费用中的哪一项？新增复杂性、接入与维护成本是什么？
3. 用哪些结果和任务判定？成功门槛、对照条件与失败后精简/调整的选择是什么？

细则集中在本文，不复制进每个 Skill。消费 Agent 只加载需要的能力说明，不承担阅读产品历史或每次画图选 npm 包的成本。
简单安全修复、错误修复与文档维护可关联父阶段的价值假设并说明影响，不必逐次运行昂贵的全量模型试验。

## 4. 三层验收，不能互相替代

**L0 工程正确性。** 类型、单元、边界、序列化、权限和浏览器检查，证明实现没有已知验收缺陷。
数学参考计算应与被测实现独立，不能让库自己出题、自己算标准答案、再自己判通过。

**L1 Agent 可用性。** 在正常配置的全新消费会话中，不读实现源码、不模拟点击编辑器即可完成发现、创作、修改和恢复。
这是 #6 的冷启动验收；脚本调用成功不等于真实模型会使用。

**L2 实际增益。** 同一 Agent 有/无 pisvis 的任务对照，证明在声明范围内值得使用。
L0/L1 通过不会自动使 L2 通过；没有对照时标“增益待验证”，不能说已经比通用 Agent 更强或更省。

实现 PR 可在功能测试和明确证据计划下合并，不要求每一根线都单独建立竞争壁垒。
但一个题型里程碑若只完成代码，尚无 L2 证据，必须区分“功能完成”和“产品增益尚未验收”；不能以已关闭 PR 代替后者。

## 5. 公平的对照方式

主比较为同一模型/版本/宿主/配置下的 G（正常通用 Agent）与 P（同一 Agent + pisvis）。
G 可以正常写代码、用其他合规依赖、运行测试、查看预览并修复；不能故意把它限制成一轮文本回答。
P 获得正常安装的库和短消费说明，但不预喂源码、答案或成功产物；不强制调用 pisvis，工具未被选用或回退也保留在结果中。

双方收到同样的题意、学科依据、视觉要求、交付目标及预算上限。
评分评价作品，不要求 G 生成 pisvis 私有格式、指定函数名或遵循我们预想的工具顺序；可编辑性通过各自产物的新会话继续修改测试。

小样本增加 K（资料消融）：给 G 相当的物理/数学与视觉说明，不给可执行 pisvis，实现与资料贡献分开分析。
若 K 已达到同样效果，说明收益可能主要来自说明资料；这并非无价值，但不能把它宣传为工程独有优势。

每次独立尝试用隔离环境、会话和产物目录，不读取另一臂产物、隐藏答案或之前试验的 Git 历史。
同一工作流内允许连续编辑；不要把一次会话的多个修改步骤当成多个独立样本。
保持相同的通用工具、合理网络权限和资源上限；环境差异必须披露。基线生成代码在无秘密的隔离环境执行，不降低库的安全标准。

冷启动与已配置后的重复使用分开；双方同等允许各自已取得的缓存/资产。
首次接入、发现和文档成本不能藏掉，不能用 P 的热路径比较 G 的第一次安装。
模型名、宿主及可获得版本信息精确记录；别名路由不透明时注明。沿用维护者已确定的评测配置，改变后另建批次。

## 6. 任务与评分应接近真实使用

从首次创作、连续改参数、保留布局/风格、并排比较、多组变式、保存恢复、长标签/小画布、错误恢复和条件不足构成完整任务。
先选窄范围做深，再扩展：当前数学能力的收益不能外推成平抛、电路或全高中物理的优势。
未支持任务同时记录缺口处理与任务交付；诚实说明不支持是正确边界行为，不等于已完成作品。

用原创任务和有权使用的资料；公开开发集用于调试，未用于调试的评测由维护者隔离管理。
不能把可读取的公开目录命名为 holdout 后声称没有泄漏；若无真正盲测，报告明确为开发集试验。
预先冻结任务版本、可公开的成功标准、参考结果、评分细则、样本数、预算与最小有意义差异；盲测的答案不得提供给消费端。
不根据结果删题、降门槛、挑最好样本或无限重跑直到赢。基础设施故障按预先规则单列，保留原记录。

评审只按任务里预先说明的交付目标，允许正确的替代实现。视觉尽量遮蔽来源/随机顺序，并说明风格可能使完全盲评不可行。
数值与交互用独立检查，教学与视觉由维护者/有相关经验的人复核；模型评审只作经过人工校准的辅助。
小样本用于查问题和判断方向，报告原始数量与分布；不足以支持统计结论时不使用“显著”“全面领先”。

## 7. 质量底线与总成本

以下维度分开报，不用一个加权总分掩盖错误：

| 维度 | 至少记录 |
| --- | --- |
| 正确、可信 | 题意/假设匹配、单位/坐标、独立数值检查、多视图一致、修改后错误 |
| 教学与视觉 | 信息层次、标签/图例、布局、风格一致、参数边界、键盘/可访问性 |
| 方便与复用 | 必要追问、额外人工提示、干预时间、修改/恢复成功率、实例隔离 |
| 时间 | 首次预览、达到交付标准、连续修改；超时和尾部延迟，不只最佳值 |
| 费用与开销 | 全程模型 usage/费用、发现与工具说明、调用/错误/重试、安装及运行资源 |
| 长期成本 | 模板开发、维护、版本迁移与接入成本；与单次调用成本分别说明 |

“合格作品”先满足本任务的题意、正确性和基本教学/视觉/操作要求。不能以错误结果、不可读标签或安全退步换取更低费用。
在质量底线成立且其他关键维度无不可接受退步时，检验预先声明的实际提升；单项结果只允许单项范围的结论，不代表所有维度已经更好。
长期追求更专业、更方便、更好看、更可复用、更省，不把一次局部领先当作停止改进的理由。

成本包括所有尝试的发现、说明阅读、执行、检查、失败修复与交付；不能只算一次 renderer 函数。
每个合格作品的成本 = 本批全部尝试的运行成本 / 合格作品数；若合格数为 0，标不可定义，不写 0。
同时报告总尝试数、成功率、预算上限与单次分布，避免只看成功样本。
人工检查/返工分钟单列；只有明确并披露工时估值时才换算金额。不能以订阅额度等同免费，费用不可获得时标 unknown。
usage 与实际账单、估算费用分开，估算注明价格来源和日期。不得虚构使用次数来摊薄研发成本。

## 8. 如何影响后续研发

开工先问“这个能力如何改善一个真实工作流”，而不是“下一项流行依赖是什么”。
新依赖要对应可测问题；已确认依赖仍需复核版本与实际价值，但不因零依赖教条重造通用基础设施。
选择能够通过测试和反馈积累优势的模型、组件、视觉规则和稳定存档；避免每道题都重新开发。
工具数量、Schema 和响应长度增加时评估消费成本；只有真实工作流显示收益，才增加组合命令或新的协议入口。

每个题型里程碑、重要模型/主题/绑定/Skill/依赖变更、模型或宿主升级时复跑相关任务。
模型变强不是停止做库的理由，也不是旧优势必然存在的证据。保留可复现的旧批次，再测新条件。
优势消失先区分样本波动、测评偏差、接入成本与真正被替代的能力，再决定精简、修复、重新定位或兼容弃用。
没有增益的层不得靠更多功能和更多术语掩盖；先做一项可验证改进。不破坏用户已有作品来追逐新架构。

**严守原则不等于拒绝改变实现。** 持续的资产积累与公平对照是方法，某个依赖、协议或封装不是不可更改的信仰。

## 9. 轻量执行与证据等级

Issue/PR 模板要求说明价值假设、关联任务、实际证据、费用/复杂性和未验证部分。
安全修复、明确 Bug 修复及纯文档任务可说明不适用端到端对照，并关联受保护的工作流；不能因为没有付费评测而阻止必要修复。
新模板、显著交互/视觉变化、重依赖和新增模型服务在父阶段交付相关对照；研发中的探索可以明确标为待验证。
这些是仓库开发与评审约定；模板复选框不等于已配置自动阻止合并的分支规则。

B1 先用现有能力交付小型任务集、轻量记录/评分与经授权的真实对照，再随 M3 扩展。
不建大评测平台，不把所有候选研究放到首个教学题型前面。
CI 默认跑不需要付费模型凭据的检查；真实 Agent 运行须在已有授权预算内，超出时先确认。
不自动安排未来付费运行；记录触发条件不等于已经设置了定时任务。

结果使用明确状态：增益假设 / 功能验证 / Agent 可用性验证 / 对照支持的范围性增益 / 证据不足 / 存在劣势。
记录源提交、包/Skill/模型/宿主与任务版本、冷热状态、全部尝试和产物、判定与缺测；清理秘密和受限资料。
B1 可以交付真实的负面结果并完成评测任务，但不能据此宣称产品增益通过；应在总纲留下改进任务。
