## M2：统一视觉 + 数学模板复用

执行 [Issue #3](https://github.com/Buqisir/pisvis/issues/3)，依赖 M1 验收。
先做最多两套真实视觉候选和 token；用向量合成/正交分解两种数学场景验证跨场景复用。
引入 Signals/Valibot 的最小适配，建立版本化实例文档、命令校验、保存/读取与两实例隔离。
不做通用公式语言、物理求解或自动布局。

建议顺序 PR：视觉样板 → 模板/校验/实例 → 交互与往返验收。
维护者未选择风格前，记录候选状态；数值与工程可以继续，不能虚构审美批准。

## M3：第一个物理题型闭环

执行 [Issue #4](https://github.com/Buqisir/pisvis/issues/4)，依赖 M2 验收。
默认采用水平抛出到水平地面、恒定重力、无阻力、质点模型；先核对教辅正文和坐标转换，独立编写测试。
同一版本化模板支持至少三组题目实例，联动情境、轨迹、速度分解、公式、函数图和读数。
用 KaTeX 与 Motion 的适配补齐排版和讲解，不用动效库替代物理时间。

建议顺序 PR：模型/来源/数值测试 → 多视图绑定 → 公式/动效/浏览器验收。
初始化的光滑斜面留作后续候选，本轮不要求两套物理模型。

## M4+：真实需求决定下一步

先选择一个能验证复用的后续小题型/装置，再决定是否需要几何、自动排版或 GPU 能力。
thi.ng、Bloom、PixiJS、TypeGPU、SceneryStack 的使用/参考全部记录在 TECH_RADAR，
试验流程见 EXPERIMENTS；它们不是五个必做的前置阶段。

反复出现的复杂几何 → 小型 thi.ng 对照；标签拥挤 → Bloom 与简单排布对照；
密集动态显示 → PixiJS 对照；明确 GPU 研究方向 → TypeGPU 独立实验；
教学交互结构 → SceneryStack 阅读/单模块评估。

未来确有消费方再加 React 适配；有具体需求再评估打印、3D、复杂求解或 Agent Tool 服务。
不设短期“覆盖全高中物理”的承诺，不把教辅题材地图当作全量开发队列。

## 每一阶段的交付口径

一个小目标、真实代码、独立数值/边界测试、可运行演示、浏览器证据、文档与已知限制。
记录依赖与官方版本来源，测试结果归属于实际运行的环境与提交。
复用要展示第二个实例/场景，风格要有真实样板，物理要有来源和假设；三者缺一不虚报完整闭环。
